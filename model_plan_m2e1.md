# Model 2 — Experiment 1 implementation plan

**Status: DRAFT FOR REVIEW. Nothing below is implemented.**

Format note: this keeps the project's established review format (the 18-section
plan-plus-pre-registered-predictions structure used for E2/E3/E4, which the project owner
specified and approved three times) and adds the task decomposition, file-responsibility
map and verification steps from the plan-writing convention. Where the two disagree, the
project's format governs.

> **For agentic workers:** implement task-by-task, checkbox by checkbox. Commit only when
> the project owner asks — this repository's convention is that the owner creates commits.

**Goal:** Determine whether a frozen pretrained vision backbone extracts more grain-size
signal from the existing tiles than Model 1's 12 hand-built features, and establish whether
the gain comes from *pretraining* rather than from *dimensionality*.

**Architecture:** One variable changes — the per-tile feature vector. Everything else is
frozen at Model 1's E3 values: the same 256 px tiles, the same two-stage
tile→image→soil median aggregation, the same StandardScaler, the same rank-3 PCA curve
basis, the same closed-form ridge, the same clip/cummax/force-100 monotone projection, the
same 16 CV families, the same trapezoid EMD. Three arms: Model 1's features as control,
frozen DINOv2 ViT-S/14 embeddings, and the **same ViT architecture with random untrained
weights** as the ablation that separates pretraining from capacity.

**Tech stack:** numpy / scipy / pandas / scikit-learn / matplotlib / Pillow (unchanged),
plus `torch` and `timm` **only on Kaggle**. A `mock` backend written in pure numpy lets the
entire pipeline run locally where torch does not exist.

**Spec:** `model_plan_m2e1.md` is the spec. The governing prior findings are
`Model 1/instructions.txt` (the instrument demotion and the two cancelled hypotheses) and
`Model 1/Model 1 Experiment 4/Experiment4.txt` §11b.

## Global constraints

- **Metric:** trapezoid EMD on log10 d, `np.trapezoid(|F - Fhat|, log10(d))`, mean over
  soils, 0–500 scale. Reconciled against the host's published trivial baseline 100.31.
  Never the page's printed left-endpoint formula, which gives 102.02 and does not reproduce
  the host's own number.
- **Primary selection metric is in-domain LOGO-CV.** This is a deliberate, declared
  exception to E3's CAM+RES ruling — see §2 for why it is legitimate here.
- **CAM+RES is demoted.** It may be *reported*, never used to select. It mis-ranked E4
  against E2 by 24.6 EMD in the wrong direction.
- **Validation:** leave-one-family-out over the 16 curve-distance families, copied
  byte-identical from E1/E2/E3. No random image-level split. The soil is the unit of
  supervision.
- **Leakage:** scaler, curve basis and any embedding transform fitted on training folds
  only. Asserted in-cell.
- **Banned inputs:** camera, device, ppm, EXIF, ICC, site, sample-id. No camera-keyed
  normalisation — E4 showed that route is circular or a metadata exploit.
- **Original data:** `data/Training/` and `data/Test/` are never read or written. Labels
  come from `manifest_samples.csv` only.
- **Preprocessing:** never re-run. `config_hash 010f44c36c74` pinned and asserted.
- **Naming:** `Submission_Model2_E1.csv`, generated by the notebook, never renamed from a
  generic file; IDs from `manifest_samples.csv` (`submission_id`, `submission_row_order`).
- **Never** overwrite or delete a previous experiment's results.
- **Local environment has no torch, no torchvision, no timm, no pytest.** Verification
  scripts are plain `python -m` modules using fail-loud `assert`, matching the existing
  `preprocess/audit.py` and `preprocess/final_check.py` convention.

## 0. Why this experiment and not another Model 1 experiment

`Model 1/instructions.txt` closed the ladder on evidence, not impatience:

| experiment | in-domain LOGO-CV | Kaggle |
|---|---|---|
| E1 | 35.98 | 172.70 |
| E2 | 42.66 | 71.27 |
| E3 | 41.15 | 61.24 |
| E4 probe | 39.46 | 77.12 |

The in-domain number never moved across four experiments. Every external gain came from
removing features and adding regularisation — variance reduction. The ~34 EMD between the
best in-domain score and the rank-3 representation ceiling of 7.35 is a signal-extraction
problem, and E3 (which families carry signal) plus E4 (which representation carries it)
both say hand-built tile summaries cannot reach it.

## 1. Why E1 is decidable without the leaderboard and without CAM+RES

This is the load-bearing methodological point, so it is stated before the design.

E1 proved LOGO-CV **ranks configurations in the wrong order for cross-camera transfer**.
That is a precise claim about one axis. It does not say LOGO-CV is a poor measure of *how
much curve signal a representation carries on devices already seen* — which is exactly the
representation question, and the only thing that was ever constant across E1–E4.

So Model 2 E1 asks a question the demoted instrument cannot corrupt:

> Does a learned representation lower in-domain error at all?

If it does not, Model 2 is refuted cheaply, on a CPU-runnable metric, with no submission
spent. If it does, we have earned the right to spend a submission discovering how the
transfer penalty behaves under a new representation.

## 2. The random-weights arm is what makes this an experiment

DINOv2 produces a 384-dim vector; Model 1 produces 12 numbers. If DINOv2 wins, the obvious
confound is capacity, not pretraining. Arm R — the identical ViT-S/14 architecture with
randomly initialised weights, same tiles, same aggregation, same head — isolates that. It
has the same dimensionality, the same receptive field, the same pipeline position.

**Without arm R this experiment answers nothing.** A win for D that does not also beat R
would be reported as "dimensionality helps", not "pretraining helps", and that distinction
is the entire point.

## 3. Physical-scale caveat, stated up front

Tiles are 256 px = 56.2 mm at the canonical 4.5525 px/mm. DINOv2 ViT-S/14 needs 224 px
input, so a tile is resized to 49.2 mm and one patch spans **3.075 mm**.

Eleven of the 24 training soils have D50 below 0.11 mm. For those, a DINOv2 patch is ~28×
the median grain — the backbone sees fines only as texture, never as particles. This is the
same resolution floor that killed particle counting during preprocessing, and it applies
to any patch-based transformer at this scale.

The fix (cropping a smaller physical area and upsampling so patches land at sub-millimetre
size) is a **different variable** and belongs in Model 2 E2. E1 deliberately does not do it,
so that a null result is interpretable: if D fails here it may be scale, not representation,
and E2 then separates them.

## 4. Head design — why no new dimensionality-reduction step

384 features on 21 training rows is degenerate-looking but ridge handles p > n in closed
form. Adding an embedding-PCA step would be a **second** change to the pipeline and would
make the comparison to Model 1 uninterpretable.

So the head is byte-for-byte Model 1's. The only accommodation is that the alpha grid is
extended upward — `{0.03 … 1e6}` — because 384 scaled features need far more shrinkage than
12, and a grid topping out at 1000 would silently under-regularise the new arms. That
extension is declared as a necessary consequence of the representation change, not an
independent variable, and it is applied to **all three arms** so the control is treated
identically.

The E4 parsimony rule carries over unchanged: where the grid optimum is not resolvable from
a larger alpha, take the larger alpha. E1's catastrophe was an oracle-chosen edge-of-grid
alpha; that failure mode is now structural policy.

## 5. File structure and responsibilities

```
Model 2/
├── instructions.txt                    WHAT Model 2 represents; promotion test; the
│                                       in-domain-primary ruling; naming convention
└── Model 2 Experiment 1/
    ├── instructions.txt                E1 scope, arms, pre-registered predictions
    ├── backbones.py                    THE BACKEND INTERFACE. Pure numpy mock + lazy
    │                                   torch branches. Only place torch is imported.
    ├── check_backbones.py              fail-loud self-check for the interface contract
    │                                   and the mock path. Runs locally, no torch.
    ├── Model2_Experiment1.ipynb        generated, not hand-edited
    ├── Experiment1.txt                 generated by the notebook from live objects
    ├── Submission_Model2_E1.csv        generated on run, if the gate passes
    └── kaggle_setup.md                 what to attach, what to enable, how to run

scratch/
├── build_m2e1.py                       notebook generator — single source of cell text
└── mk_run2.py                          regenerate + flatten to run_m2e1.py + compile-check
```

`backbones.py` is the important structural decision. In E1–E4 everything lived in notebook
cells, which was fine because everything ran locally and could be verified. Here a third
party of the code cannot run locally at all, so the torch surface must be **isolated in one
file behind a narrow interface** and everything around it must be testable without it. The
interface is three functions; two of the three backends never touch torch.

## Task 2: `backbones.py` — the interface and the mock backend

**Files:**
- Create: `Model 2/Model 2 Experiment 1/backbones.py`

**Interfaces:**
- Produces:
  - `BACKENDS = ("mock", "dinov2", "vit_random")`
  - `def embed_tiles(rgb_batch, backend: str, seed: int) -> np.ndarray`
    takes `(N,256,256,3)` float64 in 0–255, returns `(N,384)` float64. Deterministic for a
    given seed. The only function the notebook calls.
  - `def dim(backend: str) -> int` → 384 for all three arms.
  - `def requires_torch(backend: str) -> bool` → `backend != "mock"`.

- [ ] **Step 1: Write the module docstring** explaining that this is the only torch surface
  in the project and that the mock path exists because the development machine has no
  torch, so all non-backbone logic must be verifiable without it.
- [ ] **Step 2: Implement `mock`.** Deterministic numpy: fixed-seed `rng.standard_normal`
  matrix `(256*256//16, 384)` applied to a 4×-box-downsampled, per-image-standardised tile,
  then L2-normalised rows. It must be a *linear map of pixel statistics* — deliberately
  uninformative, so a mock that accidentally beat Model 1 would itself be a finding worth
  reporting.
- [ ] **Step 3: Implement `dinov2` and `vit_random`** inside the function body with
  `import torch` / `import timm` local to the branch, so importing this module never
  requires torch. `vit_random` is `timm.create_model(cfg, pretrained=False)` with a seeded
  init; `dinov2` is the same architecture with `pretrained=True` or an explicit local
  weights file. Both run `model.eval()` under `torch.no_grad()`, resize 256→224 with
  `PIL.Image.BILINEAR`, and take the **CLS token** — recorded so a later patch-mean variant
  is a visible change, not a silent one.
- [ ] **Step 4: Add a module-level cache dict** keyed by `(backend, seed)` so the model is
  built once per process.
- [ ] **Step 5: Run `python -c "import backbones"`** from the experiment folder and confirm
  it imports with no torch present.

## Task 3: `check_backbones.py` — the contract test that runs locally

**Files:**
- Create: `Model 2/Model 2 Experiment 1/check_backbones.py`

**Interfaces:**
- Consumes: `embed_tiles`, `dim`, `requires_torch`, `BACKENDS` from Task 2.
- Produces: a pass/fail script the notebook also calls before any real work.

- [ ] **Step 1: Write the assertions** —
  shape `(N,384)`; finite everywhere; deterministic (two calls with the same seed are
  bit-identical); different seeds differ; output is not all-zero; L2 row norms within 1e-6
  of 1.0; `dim()` agrees for every backend name; `requires_torch("mock") is False`;
  the mock output is invariant to a uniform brightness shift of the input (because rows are
  standardised per image), which is the property the DINOv2 arms must also be checked for.
- [ ] **Step 2: Run it.** `python check_backbones.py`. Expected: `CHECK BACKBONES: PASSED`.
- [ ] **Step 3: Confirm the torch branches fail loudly, not silently.** Call
  `embed_tiles(x, "dinov2")` and require an `ImportError` whose message names Kaggle, not a
  fallback to mock. A silent fallback would let the mock path masquerade as a result.

  Kaggle with `BACKEND=dinov2` this must fail loudly if the weights are unreachable, before

- **E embeddings** — the `check_backbones.py` call, then batched extraction over all 1,976
  materialised tiles for each active arm, cached to `.cache/embed_<backend>_<config_hash>_<seed>.npy`.

- **H in-domain scoring** — LOGO-CV per arm per alpha, nested, with the E4 parsimony rule

- **J mechanism** — camera shift and sharpness shift in SD for the embedding arms vs the

- **K report-only ruler** — CAM+RES for all three arms, printed with an explicit header

- **L gate** — the submission decision from §6, executed as code so it cannot be
  renegotiated after seeing numbers.
- **M submission** — if the gate passes: fit, 8 gates, write `Submission_Model2_E1.csv`.
  If not: write nothing and print the reason.
- **N error analysis** — curve plots vs E3, saturation, per-soil difference strip.
- **O record** — write `Experiment1.txt` from live objects, including the predictions

## 6. The decision gate — fixed before the run, executed as code

```
submit = (in_domain(D) < in_domain(M1_C0))  AND  (in_domain(D) < in_domain(R))
         AND the paired soil-bootstrap CI of D-vs-R excludes zero
```

| outcome | meaning | action |
|---|---|---|
| D beats control and beats random-init | pretraining extracts real signal | submit; gain a 5th calibration point |
| D beats control but not random-init | it is **capacity**, not pretraining | do not submit; Model 2 E2 tests magnification instead |
| D does not beat control | representation is not the bottleneck | do not submit; the 34 EMD headroom is a data limit at n=24 and the project's remaining time goes to robustness of Model 1, not new representations |

The second and third rows are real possibilities and both are useful answers. This
experiment is designed to be refutable, not to be vindicated.

## 7. Pre-registered predictions

Written before implementation. The blind/confirmation label is per prediction and may not
be edited afterwards.

| # | prediction | blind? |
|---|---|---|
| P1 | mock's in-domain LOGO-CV is worse than the no-image floor 82.62 | no — a plumbing correctness check; if it fails, the pipeline leaks |
| P2 | DINOv2 embeddings shift **less** between Motorola and Samsung than the colour block does (colour mean camera shift 1.54 z) | **YES** |
| P3 | random-init arm R does not beat Model 1's control in-domain | **YES** — and this is the ablation the experiment rests on |
| P4 | DINOv2 arm D beats Model 1's control in-domain | **YES** — the central claim |
| P5 | D beats R by a paired margin whose CI excludes zero | **YES** — pretraining, not capacity |
| P6 | if a submission is made it beats 61.24 | **YES** — the only external test |

P4 and P5 must both hold for the gate to fire. P2 is diagnostic: if learned features are
*not* more camera-stable, Model 2 inherits Model 1's transfer wall in full and the
robustness work has to be done regardless of representation.

## 8. Assumptions

- Kaggle's image has `torch` and `timm`. **Unverified from here.** Task 6 Step 1 mitigates
  rather than assumes: arm R needs no weights, and the environment probe fails loudly
  before any long compute. If `timm` is absent, the fallback is `torch.hub` with internet
  on; if both fail, `torchvision.models.convnext_tiny` supervised-ImageNet is an acceptable
  substitute and the plan's logic survives, because the random-init ablation is
  architecture-agnostic.
- The public 3-soil subset is unchanged across E1–E4 and Model 2. Every calibration point
  depends on this. Untestable from our side; it is the largest assumption in the project.
- DINOv2 ViT-S/14 weights are reachable offline via a Kaggle dataset
  (`busyaprime/dinov2-vits14-timm-weights` exists) or by enabling internet once.

## 9. Risks

1. **No local verification of the backbone path.** Mitigated by isolating torch in one
   file behind a tested interface, plus the mock dry run that exercises everything else.
   Not eliminated. Budget two or three Kaggle runs for plumbing.
2. **384 features on 21 rows.** Ridge handles it but the effective degrees of freedom are
   enormous. The extended alpha grid plus the E4 parsimony rule are the guard; expect the
   selected alpha to be large and the fitted model to be nearly a constant predictor. If
   the winning configuration is indistinguishable from the mean curve, that is the honest
   finding, not a bug.
3. **Scale mismatch (§3) may dominate.** A null for D could mean "wrong magnification"
   rather than "learned features do not help." P3/P5 partially separate this, and E2's
   crop-and-upsample arm resolves it, but E1 alone cannot fully exclude it.
4. **CLS-only pooling is a silent choice.** Recorded in Task 2 Step 3 so a patch-mean
   variant is a visible later change rather than an untracked drift.
5. **Pretraining gains may be real and still lose on the leaderboard**, because the
   transfer penalty is untouched by this experiment. That is the point of the gate: E1
   earns information about representation, not about deployment.

## 10. What this decides

- Gate fires → Model 2 continues; E2 attacks the physical scale of the patch, and the
  camera-invariance work moves into Model 2 where E4 said it belongs.
- Capacity-only result → drop the pretrained line, keep the dimensionality insight, and
  revisit Model 1's feature count with the ruler's warnings in force.
- Null → the 24-soil dataset is the binding constraint. Remaining time goes to squeezing
  the 61.24 configuration — ensembling, calibration of the curve output, and robustness —
  rather than to new representations.

## 11. Cost

Local mock dry run: about 3 minutes, CPU, free.
Kaggle: embedding extraction is 1,976 tiles through a 21M-parameter frozen ViT-S/14 at
batch 64 — well under a minute on one T4. No training, no gradient, no checkpointing. The
whole notebook should finish inside 6 minutes including the nested sweeps.
